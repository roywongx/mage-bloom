# 07 · AI 评审指南

> 给外部评审 AI/工程师：请按本文顺序阅读，用 §3 的不变量与 §4 的问题清单挑战设计。目标不是"看着合理"，而是找出**会导致错误施法、性能问题、维护灾难**的具体缺陷。

## 1. 背景（30 秒）

- 目标游戏：魔兽世界：无限（`_forever_` 1.60.1，Interface 16001），法师三系。
- 迭代对象：小六月 LiuyueForever 1.3.4（无限服一键插件）。
- 本仓库当前只有设计，没有实现；请评审**设计是否可落地**。
- 关键约束：战斗锁定下只能"点击瞬间在受限环境改安全属性"；一次按键一次动作。

## 3. 必须成立的不变量

| # | 不变量 | 违反后果 |
| --- | --- | --- |
| I1 | 决策是纯函数：同状态同配置同结果 | 无法测试、无法复现 |
| I2 | 决策不调用任何写 API | 污染、战斗锁定报错 |
| I3 | 一次按键最多一次施法 | 变成自动战斗 |
| I4 | 死亡/无目标/未学会/蓝不够/超距 → 不推荐 | 空放、浪费 GCD |
| I5 | 引导中不推荐需要读条的技能 | 断引导，DPS 暴跌 |
| I6 | 触发类判定必须用 spellId，不用名称 | rank/来源变更即失效 |
| I7 | 战斗中不重建按钮、不改绑定 | 污染/报错 |
| I8 | 信道未提交（双宽度不一致）时不施法 | 施错技能 |
| I9 | 规则数 ≤ 16，且按优先级截断 | snippet 过长/宽度冲突 |
| I10 | 每个数字有来源或标 TODO | 不可维护的魔法数 |
| I11 | profile 变更必须带 golden 与 changelog | 回归不可控 |
| I12 | 默认配置不自动开爆发/不自动吃宝石 | 玩家失去控制权 |

## 4. 重点挑战清单

### 4.1 APL 正确性

- 冰法：寒冰指期间为什么先冰枪而不是继续寒冰箭？冰枪 8 秒 CD 是否需要在规则里显式 `cd`？
- 火法：热力迸发 =3 层才炎爆，是否会在读条中误判？`notCasting` 是否足够？
- 火法：灼烧维持的 `debuffBelow` 语义（层数 <5 **或** 剩余 <5）是否会与"正在施放灼烧"冲突？
- 奥法：奥冲层数用 `maxStacks=3`，在第 4 层时是否会错误地继续奥冲？
- 奥法：气定神闲 + 奥术愤怒的时序，在一键点击下是否会吞掉 PoM？
- AOE：姓名板计数在遮挡/多怪场景是否可靠？有没有更稳的替代（战斗日志/焦点）？
- 移动：只靠 `IsMoving` 是否足够？后退/侧移/跳跃的边界？

### 4.2 状态与 API

- `C_UnitAuras` 在被限制的客户端构建上是否存在？回退路径是否完整？
- 光环扫描 80 次/100ms 的开销是否可接受？是否需要按需查询？
- `IsSpellUsable` 在冷却中返回什么？是否会把"CD 中"误判为"可用"？
- `GetSpellCooldown` 与 GCD 的区分是否可靠？
- 目标切换、假死、免疫、反射（法术反制）如何处理？

### 4.3 派发通道

- 宽度编码的量化误差在 4K/UI scale 下是否稳定？
- `SecureHandlerWrapScript` 前置体是否可以安全地 `SetAttribute`？有没有更简单的官方路径？
- 16 条规则的 snippet 是否会被客户端限制？
- 双 tooltip 提交在延迟/丢帧时是否会读到旧值？
- 信道失败时"不施法"的降级是否会让玩家以为插件坏了？提示是否充分？

### 4.4 性能

- 10 Hz 快照 + 扫描是否会在 40 人团本掉帧？
- 热路径是否有隐式分配（闭包、字符串拼接、`table.concat`）？
- trace 环形缓冲是否会无限增长？

### 4.5 测试

- parity 的"一致率"是否会被大量简单状态稀释？是否需要按规则加权？
- 木桩 A/B 的样本量与统计方法是否站得住？
- 如何证明"没有断引导"而不是"日志里看不到"？

### 4.6 兼容与维护

- 小六月升级后 hook 失效如何自动降级？
- 与新版客户端（1.60.2+）不兼容时的行为？
- 与 WeakAuras/BD-PVE/其他一键插件冲突如何检测？
- profile 的 schema 版本迁移策略？

## 5. 评分表（建议）

| 维度 | 权重 | 通过标准 |
| --- | --- | --- |
| 目标与指标 | 15% | 指标可测量、阈值合理 |
| 机制事实 | 20% | ID/阈值有来源，冲突有标注 |
| APL 语义 | 20% | 条件可表达、顺序正确、无反模式 |
| 执行安全 | 20% | 不变量 I2/I3/I7/I8 全部满足 |
| 可测试性 | 15% | 离线可复现、有 parity/AB 方案 |
| 可维护性 | 10% | 数据/引擎分离、版本与迁移清楚 |

**P0（阻塞）**：会导致错误施法、污染、自动战斗、不可复现。
**P1（重要）**：会导致 DPS 明显损失或维护困难。
**P2（建议）**：文档、命名、体验。

## 6. 常见错误模式（请重点抓）

- 把"优先级列表"写成"if/else 硬编码"，导致无法数据化；
- 用技能名称判定触发（版本一改就废）；
- 忽略引导/读条状态，推荐新技能；
- 在 tick 里直接施法（违反一次按键一次动作）；
- 用"模拟器说对"代替实机验证；
- 指标定义含糊（"更高 DPS"没有样本量与置信区间）；
- 把未验证的 ID 写进默认 profile。

## 7. 如何提交评审

- 以 Issue 形式：标题 `[review][P0/P1/P2] <一句话>`；
- 正文：引用文档章节 + 具体反例（状态/规则/时序）+ 建议；
- 若涉及数据：附来源链接或实测日志；
- 不要提"加个自动走路/自动选怪"这类超出非目标的需求。

## 8. 评审后我们会做什么

- P0：当轮修复，更新 ADR；
- P1：进入里程碑 backlog，标注验收指标；
- P2：合并到文档/命名清理；
- 所有采纳项在 `CHANGELOG.md` 记录（谁提的、改了什么、为什么）。
