# 13 · 本机控制栈研究（wow-ah / Stormwind / ESP32）

> 对象：`~/wow-ah`（Forever 线 + 泰坦线）、`~/wow-esp32s3/host`（HID 控制）、
> `addon-forever/TitanForever`（状态导出插件）、`mac/`（抓屏/解码/推送）。
> 目的：为 Mage Bloom v2 提炼可复用接口与硬约束，避免重复造轮子。

## 1. 结论先行

这套栈已经解决了分布式战斗系统最难的三个问题：

| 问题 | 现成答案 | 位置 |
| --- | --- | --- |
| 高频结构化状态从游戏里出来 | 插件画 128×12 色块（JSON + CRC），Mac 本机解码，DGX 读内存 | `TitanForever/Core.lua`、`mac/ctlcodec.py`、`mac/push.py`、`statehub.py` |
| 唯一合法的输入通道 | ESP32-S3 USB HID，租约串行化，闸门 fail-closed | `esp32d.py`、`wowctl.py` |
| “动作成功”的判据 | 只认外部证据（数量/金币/窗口/GCD/光环），不认 ACK | `stormwind/control.py`、`drive.py`、`frames.py` |

Mage Bloom v2 不需要重写这三层；需要新增的是**战斗态字段**（光环、GCD、冷却、资源、目标 debuff）和**Windows 侧采集**。

## 2. 拓扑

```
游戏客户端（Mac _forever_）
  ├─ 插件 TitanForever
  │    ├─ 128×12 色块（4608 B，TC01 JSON，CRC16，≤4574 B 载荷，5–10 Hz）
  │    └─ /tf、/tc 命令 + 安全按钮（仅脱战 arm）
  ↓ 窗口捕获（ScreenCaptureKit，窗口级、无损 BMP，10–15 fps）
Mac 常驻
  ├─ foreverread：解码 60 B 位姿条 → forever-state.json（10 Hz）
  └─ push.py：解码 128×12 控制块（~5 ms）→ TCP JSON 行 → DGX:8893
DGX
  ├─ statehub：每类只留最新一帧，带 age；过期即 ok=false
  ├─ wowctl：state()/control()/hub()，严格帧校验（stale/degraded/missing 抛错）
  └─ esp32d:8897：租约 + 闸门 + HID → ESP32-S3 → 游戏
```

关键点：**DGX 不直接碰游戏**；它读的是“已经解码好的字段”，写的是“硬件按键”。

## 3. 接口清单

| 接口 | 契约 | 延迟/频率 | 备注 |
| --- | --- | --- | --- |
| `wowctl.state()` | 位姿必须 `ok=true, stale=false, at` 在 2 s 内 | 10 Hz | 缺字段抛 `Missing`，过期抛 `Stale` |
| `wowctl.control()` | 控制帧无 `error`、无 `minimal`、`at_local` 在 5 s 内 | 5 Hz | 读 statehub 内存，不开 SSH |
| `wowctl.hub(kind)` | `pose/gate/control/hdt` 最新一帧 | 4–10 Hz | 中枢没开就抛错，不回退旧路径 |
| `wowctl.esp(path, **p)` | HTTP GET，带租约 token | 单次 | `423` 租约、`503` 闸门、`409` 急停 |
| `wowctl.lease(owner, ttl)` | 全局唯一输入锁，自动续期，进程死自动松 | 15–600 s | 嵌套复用同一 token |
| `wowctl.chat(text)` | 只允许 `/` 开头、无逗号；先 `/` 再补字符再回车 | ~300 ms | 回车白名单由 esp32d 校验 |
| `wowctl.goto(x,y)` | 光标闭环，3 px 容差 | 40 次迭代上限 | 只移动、不点击 |
| `control.ask(verb)` | 一问一答，答案 <200 B | ~200 ms | 把大转储压成谓词查询 |

## 4. 协议与字段

### 4.1 位姿条（60 B）

`TitanForever/Core.lua` 复用 TitanStrip 的 28×K 布局：x/y/facing 塞在 `mainAt/appAt/lastBookAt`，flags 是 u16。Mac `stripread` 解码成 `forever-state.json`。

### 4.2 控制块（128×12）

- 4 物理像素一格，总 4608 B；前 8 格是 finder/校准，其余是 `TC01 | len u16 | seq u16 | JSON | CRC16`。
- `MAX_PAYLOAD = 4574 B`，JSON `sort_keys` 保证可 diff。
- 解码失败（缺格、CRC、截断）一律 `ValueError`，调用方必须当“未知”。

**现有 JSON 字段（战斗相关）**：

| 字段 | 含义 |
| --- | --- |
| `at`, `uptime`, `seq` | 服务器时间 / 运行时长 / 序号 |
| `money`, `counts`, `bag_items` | 金币 / 背包计数 / 物品 |
| `target` | `{name, npc_id, distance_sq}`，GUID 派生 |
| `casting` | `{id, name}`，玩家当前读条 |
| `speed` | `GetUnitSpeed`，判断是否被钉住 |
| `dead`, `dead_now` | 死亡 |
| `windows` | 拍卖/邮箱/商人/训练师等窗口 |
| `buttons`, `recipes`, `gossip` | 归一化矩形，供点击 |
| `chat_log`, `answer` | 聊天回执 / 谓词回答 |
| `lastAction` | `requested/done/error`，插件侧动作痕迹 |

**flags 位**：`ahOpen 0x0002`、`inCombat 0x0004`、`scanOn 0x0008`、`mailOpen 0x0010`、`mailGm 0x0020`、`throttled 0x0040`、`typing 0x0080`、`errors 0x0100`、`paused 0x0200`、`vendorOpen 0x0400`、`trainerOpen 0x0800`、`dead 0x1000`、`resting 0x2000`。

### 4.3 插件命令面

- `/tf scan|status|keep|meta|interact|targetexact|vbuy|openskill|gossip|train|route|recipes`
- `/tc`：`t` 选目标、`g` 对话选项、`q` 谓词查询、`chatlog`、`exec`。
- 安全按钮 `TitanCtlActionButton` 可 `arm(kind,id)`，但 **`InCombatLockdown()` 时拒绝**；`PostClick` 只记 `requested`。

## 5. 五条可复用契约（最重要）

1. **读 = 结构化帧**：色块/位姿条是编码，不是视频；不做 OCR、不把原图送模型。
2. **读不到 ≠ 0**：`frames.py` 把 `Stale / Degraded / Missing` 分开；缺字段绝不当默认值。
3. **写 = 硬件 HID**：不注入进程、不调受保护 API；租约串行化，持键必须带 token。
4. **验收 = 外部证据**：买看数量+金币，制造看材料−N/成品+1，开窗看 flags；`requested` 永远不算成功。
5. **未知 = 停**：无回执不重发；reload 前等 SavedVariables mtime；掉线只按 3724 连接数/色条判。

## 6. 映射到 Mage Bloom v2

### 6.1 需要新增的战斗态字段

现有控制块只够做“走路/买/卖”，不够做循环。建议新增（同一 4574 B 预算内）：

```json
{
  "gcd": 0.42,
  "mana": [4210, 5210],
  "hp": [0.86, 1.0],
  "cast": {"id": 8407, "remain": 1.2, "channel": false},
  "buffs": [{"id": 400625, "n": 3, "rem": 12.4}, {"id": 400669, "n": 1, "rem": 9.8}],
  "cds": {"1240047": 5.2, "2139": 0},
  "target": {"guid": "...", "hp": 0.62, "casting": {"id": 12345, "remain": 0.8, "interruptible": true}},
  "debuffs": [{"id": 22959, "n": 5, "rem": 7.1}]
}
```

30 个光环 + 10 个冷却 ≈ 1.5–2 KB，余量足够。仍需保留 `seq/at` 与 CRC。

### 6.2 执行

- 不用服务器 API，也不依赖 `arm`（战斗中拒绝）。
- 用 **HID 按键** 打玩家自己的动作条/键位；DGX 只决定“按哪个键”。
- 技能→键位映射写在配置里；切换专精时校验（键位缺失 = 安全停手）。
- 打断/保命走**本地快路径**：状态帧里 `target.casting.interruptible && remain < 1.2` 时，DGX 立即发键；超过 200 ms 未确认就放弃，不在最后一刻赌往返。

### 6.3 验收

| 动作 | 证据 |
| --- | --- |
| 施法成功 | 下一次状态帧出现 GCD + 目标 debuff/自身 buff 变化 |
| 打断成功 | 目标 `casting` 消失 + 法术系锁（若可读） |
| 保命 | 护盾 buff 出现 / 血量停止下降 |
| 切目标 | `target.guid` 变化 + 后续技能命中该 GUID |

### 6.4 延迟预算（按现有实现）

| 段 | 实测/代码依据 | 预算 |
| --- | --- | --- |
| 色块 → Mac 解码 | `ctlcodec` ~5 ms，push 5 Hz | 100–200 ms |
| DGX 决策 | APL 2 ms，2–3 GCD 10 ms | ≤10 ms |
| HID 按键 | esp32d + 固件 | 20–50 ms |
| 游戏 tick + 状态回传 | 下一次帧 | 100–200 ms |
| **端到端** | | **150–300 ms p99** |

所以“100 ms p99”不现实；GCD 1.5 s 够用，打断必须预判/本地兜底。

## 7. 环境差异（必须先确认）

| 项 | 现状 | 影响 |
| --- | --- | --- |
| 客户端位置 | 抓屏/解码栈跑在 **Mac** `_forever_`；你的游戏在 **Windows** `_forever_` | DGX 要控制 Windows，必须移植采集/解码/推送，或把游戏搬到 Mac |
| 抓屏 | macOS ScreenCaptureKit，窗口级无损 | Windows 需要 GDI/DXGI 窗口捕获，颜色管理必须逐字节校验 |
| ESP32 归属 | `esp32d` 127.0.0.1:8897，HID 必须插在“运行游戏的那台机器” | 插错机器 = 一个键都进不了游戏 |
| 插件 | `TitanForever` 只在 Mac 客户端 | Windows 需要装同款/新 `MageCtl` |
| 账号 | 同一账号不能同时两地在线 | 控制端与手动端必须分开 |

## 8. F0：最小闭环（建议本周做）

**目标**：证明 `DGX 状态 → 决策 → HID 按键 → 游戏施法 → 状态证据` 成立。

1. `MageCtl` 只导出：`gcd/mana/cast/target/buffs(寒冰指)/cds(法术反制)`。
2. DGX 规则：`target.casting.interruptible && cds[2139]==0 && gcd<0.2` → 按反制键。
3. 验收：下一帧 `target.casting` 消失；若 300 ms 内未消失，记 `timeout`，不重按。
4. 指标：端到端 p50/p99、成功率、误按率、状态丢失次数。
5. 通过后再接 APL；不通过就先修采集/输入，不写预测器。

## 9. 风险

- **Warden/行为检测**：HID 只解决“输入来源”，不解决“完美时序”；仍需人类化（20–80 ms 抖动、APM 上限、停顿）。
- **战斗中建帧**：色块必须在脱战预建；战斗中只改纹理颜色。
- **动作条映射**：换专精/换键位会让“按哪个键”失效；启动时校验并拒绝运行。
- **双客户端**：Mac/Windows 状态与账号不能混用。
- **色块容量**：4574 B 是硬上限；字段超了会 `minimal` 降级，必须按优先级裁剪。
