# 15 · 双模态（PvE/PvP）、常驻监控与自愈

> 目标：同一套助手，按场景切换 PvE / PvP 规则；常驻结构化监控发现异常并分级自愈；
> 特殊情况下允许“自动打断/自动保命”这类单点自动化，但必须是用户显式开启、有边界、可回滚。

## 1. 双模态状态机

### 1.1 模式

| 模式 | 用途 | 规则来源 |
| --- | --- | --- |
| `AUTO` | 默认，自动判 PvE/PvP | 状态机 |
| `PVE` | 副本/野外/木桩 | `profiles/mage/pve/*` |
| `PVP` | 竞技场/战场/野外 PvP | `profiles/mage/pvp/*` |
| `OFF` | 只观测，不建议/不 assist | — |

用户可在 `/assist` 面板强制指定；`AUTO` 下由信号判定 + 滞回。

### 1.2 判定信号

| 信号 | 读法 | 权重 |
| --- | --- | --- |
| 实例类型 | `IsInInstance()` → `arena`/`pvp` | 强 |
| 区域 PvP 类型 | `GetZonePVPInfo()` → `arena`/`combat`/`hostile` | 强 |
| 目标是玩家 | `UnitIsPlayer("target")` | 强 |
| 姓名板有玩家 | `C_NamePlate` + `UnitIsPlayer` | 中 |
| 玩家 PvP 标记 | `UnitIsPVP("player")` | 中 |
| 战场事件 | `PLAYER_ENTERING_BATTLEGROUND` 等 | 强 |
| 竞技场框体 | `arena1-3` 存在 | 强 |

**滞回**：连续 1 s 满足 ≥2 个强信号 → 进 PvP；脱离战斗且 5 s 无信号 → 回 PvE。避免门口/插旗来回抖。

### 1.3 技能集完全不同

| 专精 | PvE 主力 | PvP 主力 |
| --- | --- | --- |
| 冰 | 寒冰箭、暴风雪、冰锥、冰枪（寒冰指）、寒冰护体、唤醒 | 冰霜新星、冰锥、变形术、法术反制、寒冰屏障、闪现、冰枪（碎冰） |
| 火 | 火球、灼烧、炎爆（热力迸发）、烈焰风暴、燃烧 | 火焰冲击、灼烧、炎爆、变形术、法术反制、寒冰屏障、闪现 |
| 奥 | 奥冲、奥弹（飞弹连射）、奥术愤怒、奥爆、唤醒 | 奥冲、奥弹、气定+奥怒、法术反制、寒冰屏障、闪现 |

规则文件按 `pve/`、`pvp/` 分目录，禁止混用；切换时重新编译（脱战）。

## 2. 常驻监控（独立于战斗决策）

### 2.1 两条通道

| 通道 | 频率 | 用途 |
| --- | --- | --- |
| CombatState（addon 色块） | 10 Hz | 技能/光环/GCD/冷却/目标 |
| 像素看门狗 | 5 Hz（异常时 15 Hz） | 场景切换、施法条、血条、UI 异常 |

看门狗只做**低成本的固定点采样**，不参与逐帧决策；异常时才提高频率。

### 2.2 监控项

| 类别 | 具体 | 判定 |
| --- | --- | --- |
| 场景 | 进入 PvP / 离开 PvP / 进副本 / 回城 | 信号 + 滞回 |
| 状态 | 色块 stale、CRC 失败、字段缺失 | `frames.py` 语义 |
| 动作 | 发了技能但 300 ms 内无 GCD/光环变化 | `no_effect` |
| 像素 | 校准失败、施法条读不到、血条突变 | `pixel_fault` |
| 插件 | Lua 报错、AddOn 被禁用、版本不匹配 | `addon_fault` |
| 角色 | 死亡、卡住（按 W 速度 0）、掉线 | `stuck`/`dead` |
| 规则 | 当前模式与 profile 不匹配、技能未学 | `profile_fault` |

### 2.3 异常记录

每次异常写一条 `incident`：

```json
{"at": 1760000000.1, "kind": "no_effect", "mode": "PVP",
 "state_seq": 10231, "action": {"key": "f", "spell": 2139},
 "evidence": {"gcd_before": 0.0, "gcd_after": 1.4, "target_casting": false},
 "repair": "R1"}
```

## 3. 分级自愈（先保守，绝不盲按）

| 级别 | 触发 | 动作 | 约束 |
| --- | --- | --- | --- |
| R0 | 单帧 stale/丢包 | 重读下一帧 | 不动作 |
| R1 | 连续 3 帧异常 / 像素校准失败 | 重标定、重置采样、切保守 profile | 不按键 |
| R2 | `no_effect` 连续 2 次 | 关闭 L2 assist/自动打断，退回纯建议 | 战斗中可做 |
| R3 | 插件报错/版本不匹配 | 脱战 `/reload` 或重装 addon | 仅脱战 |
| R4 | 掉线/卡死 | 走 `relogin`（3724 连接数/色条判据） | 有预算、有证据 |
| R5 | 无法恢复 | 停手 + 通知人（TTS/面板红灯） | 不猜 |

硬规则：

- 战斗中只允许“降级/停用”，不允许重启客户端、改键位、改插件。
- 任何自愈动作都要有**前后证据**；没有证据的“修复”视为失败。
- 自愈失败不重试超过 2 次；第 3 次交给人。

## 4. 学习与迭代（离线，不热改）

### 4.1 数据

- 每场战斗保存：状态序列、决策、实际动作、结果（GCD/光环/血量/死亡）。
- 标签：模式、专精、对手职业/专精猜测、胜负、异常。
- 存储：本地 SQLite/JSONL，不上传。

### 4.2 循环

```
采集 → 回放 → 指标（DPS/打断/存活/触发利用率）
     → 参数搜索/规则对比 → 生成候选 profile
     → 离线 A/B（同状态语料） → 人工审批 → 发布 → 可回滚
```

- 实时路径**不允许**自修改代码/规则；只允许读取已发布的 profile。
- 自动调参仅限阈值（唤醒法力、AOE 数、反应窗口），且有上下界与回滚。
- 模型只做离线复盘/对手习惯，输出 `model_version` + `confidence`。

## 5. 特殊情况自动化（可选）

### 5.1 自动打断

| 项 | 规则 |
| --- | --- |
| 开关 | 用户显式开启，默认关 |
| 条件 | 目标可打断、剩余 > 0.3 s、反制可用、距离够、模式 PvP（或 PvE 危险法术） |
| 去重 | 同一 `guid + castID` 只按一次 |
| 频率 | 两次自动打断至少间隔 8 s |
| 证据 | 300 ms 内目标 casting 消失；否则记失败，不重按 |
| 回退 | 状态 stale / 像素冲突 / 玩家正在打字 → 不按 |
| 人类化 | 反应延迟 80–150 ms 抖动，不 0 ms |

### 5.2 自动保命

- 血量阈值 + 来袭伤害/敌方爆发冷却 + 护盾/冰箱可用。
- 每次战斗最多 N 次；优先提示，用户开启后才自动。

### 5.3 明确不做

- 自动选目标、自动移动、自动走位、自动开怪、全自动循环。
- 自动打断的“连锁控制”：一次只做一个动作。

## 6. 架构

```
addon MageCtl ── 10 Hz CombatState（含 mode/flags/errors）
        │
        ├─ 像素看门狗（5 Hz，异常 15 Hz）── 场景/施法条/血条/校准
        ▼
本地 agent（Windows/Mac）
        ├─ 模式状态机（AUTO/PVE/PVP，滞回）
        ├─ 异常检测 + 自愈 R0–R5
        └─ 转发 DGX
        ▼
DGX brain
        ├─ 模式路由 → PvE APL / PvP 规则
        ├─ 建议队列（next 3 + reason）
        ├─ 可选自动打断/保命（受开关与边界）
        └─ 记录/回放/离线学习
        ▼
/assist 面板 + TTS + 可选 L2 assist 键
```

## 8. 路线图增量

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| B1 | 模式状态机 + PvE/PvP profile 分目录 | 切换不抖动，脱战重编译 |
| B2 | 像素看门狗 + 异常记录 | 场景切换识别 ≥99%，异常可回放 |
| B3 | 自愈 R0–R2 | 不误按，降级可恢复 |
| B4 | 自动打断（可选） | 一次施法一次按键，成功率/误按率可量化 |
| B5 | 离线学习循环 | 候选 profile 有 A/B 数据才发布 |
| B6 | R3–R5（reload/relogin/通知） | 有证据、有预算、可急停 |

## 9. 与检测的关系

- 自动打断是**无按键输入**，行为特征最强；默认关，开启后必须人类化 + 频率上限。
- 自愈的 `/reload`、重登也是显眼动作，只在脱战/掉线时做。
- 监控本身不产生输入，风险最低；优先把监控做全。

## 10. Windows 采集前提与 F0 验收修正

- 采集端在 **Windows 游戏机**：WGC 优先、DXGI 备选、GDI 诊断；协议仍是 128×12 / TC01 / CRC16。
- 模式状态机与看门狗都消费同一份 `CombatState`；像素只提供数值，不送模型。
- F0 的“反制成功”不能用“目标 casting 消失”单独判定：优先 `SPELL_INTERRUPT` 事件；
  没有事件时结合 GUID、反制冷却、施法结束时序标 `inferred`；超时只代表 `unconfirmed`，不是失败。
- 详细契约见 [16 Windows 采集与 F0](16-Windows采集与F0.md)。
