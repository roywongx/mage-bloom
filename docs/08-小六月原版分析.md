# 08 · 小六月原版分析（LiuyueForever 1.3.4）

> 分析对象：新手盒子分发的 `LiuyueForever-1.3.4-public`（12,843,788 字节，ZIP）。
> 目的：理解其架构与取舍，决定"继承什么、替换什么"。
> 声明：本文只记录架构与行为，不复制其代码；本项目不包含、不再分发其源码与素材。

## 3. 混淆

- 所有字符串字面量被逐字节 **XOR 123** 后写成十进制转义，由 `__LFd(s)` 还原并缓存。
- 代码逻辑（控制流、条件、表结构）是明文。
- 本次分析共还原 12,217 个字符串。
- 结论：混淆只增加阅读成本，不构成保护；对可维护性是负资产。

## 4. 安全派发（核心资产）

`Engine/Smart.lua` 的实现：

1. 创建 `SecureActionButtonTemplate, SecureHandlerBaseTemplate` 按钮；
2. 两个隐藏 `GameTooltip`（`SecureFrameTemplate`）作为数据/提交通道；
3. 把"规则索引"编码为 `SetPadding` 宽度：`16 + index × 32`；
4. 编译时对每条规则标定宽度，写入 `widths`；
5. `SecureHandlerWrapScript(button, "OnClick", button, snippet)`：点击前置体读取两个 tooltip 宽度，宽度一致才 `SetAttribute("type","spell")` / `spell` / `unit`；
6. 无匹配则清空 `type`，本次点击不施法；
7. `MAX_RULES = 16`。

这套机制的优点是：**在不违反战斗锁定的前提下，把不安全代码的实时决策传进安全执行**。缺点是：宽度量化、UI scale 敏感、规则数受限、失败模式隐蔽。

我们的方案保留思想，补齐：标定校验、双通道一致性、失败降级、trace、上限校验。

## 5. APL 引擎

- 数据：`A.DATA[class][spec] = { rule, ... }`，规则字段包括 `spell/id/target/cd/burst/finisher/cp/energy/rage/mana/aoe/buffMissing/debuffMissing/refreshBelow/debuffStacksBelow/notChanneling/moving/...`。
- 解析：`Resolve(name)` 通过 `GetSpellInfo` 与别名表把名称映射到 ID；`SpellBook` 提供学习等级。
- 求值：`PickIndex` → `EffectiveChain` → 逐条 `Meets(rule, state)`；`gateMeets` 额外处理冷却账本、距离、DoT 保护、打断、形态等。
- 兜底：`FallbackIndex` 在没有规则命中时选一个"安全填充"。
- 自定义：`AplString` 定义 `LYF1.` 前缀，`key=value;...` 以 `|` 分隔，最多 30 条/8000 字符。

### 条件集（关键缺口）

已有：`cd`、`target`、`mana`、`energy`、`rage`、`cp`、`finisher`、`aoe`、`aoeClose`、`moving`、`notChanneling`、`playerHpBelow`、`healBelow`、`targetHpBelow`、`buffMissing`、`debuffMissing`、`refreshBelow`、`debuffStacksBelow`、`interrupt`、`burst`、`once`、`phase`。

缺失（对法师致命）：

- **buff 存在且层数 ≥ N**（无法表达"寒冰指 ≥1""热力迸发 =3""奥冲 <4"）；
- **buff 剩余时间 < N**（无法在窗口结束前打出去）；
- **AOE 与触发组合**（如"3 目标且寒冰指"）；
- **施法/引导的精细判断**（只有 `notChanneling`，没有"正在施放某技能"）；
- **技能可用性/距离的显式语义**（依赖隐式解析）。

## 6. 法师数据现状

- 内置三套 MAGE 表，各 3–4 条，无触发、无 AOE、无法力管理；
- `RotationTips` 的法师文案反而是对的（灼烧 5 层、暴击炎爆、冰枪看寒冰指），但**引擎表达不出来**；
- `SpellBook` 已收录无限服自定义技能 ID（冰枪 1240047、奥冲 1239700、奥术愤怒 1326082、霜火 1237313），说明作者知道机制，但没落到 APL。

## 7. 评估

### 7.1 值得继承

| 设计 | 原因 |
| --- | --- |
| 安全信道 | 目前唯一稳定的战斗内动态派发路径 |
| 一键按钮 + 专精自动识别 | 交互简单，切专精不重载 |
| 策略/外壳分离 | 便于社区贡献与多职业扩展 |
| APL 字符串生态 | 玩家可分享策略，降低使用门槛 |
| 多职业数据表 | 提供了大量技能 ID/等级，可作为数据源交叉验证 |

### 7.2 必须替换

| 设计 | 原因 |
| --- | --- |
| 法师 APL | 规则过薄，无法覆盖触发/AOE/法力 |
| 条件集 | 缺少层数/剩余/施法状态，表达力不足 |
| 字符串混淆 | 阻碍审阅与社区贡献 |
| 320 KB 单文件 | 不可维护、不可测试 |
| 无 trace | 出问题只能猜 |
| 无测试/无版本化 | 改动不可回归 |
| 名称解析优先 | rank/来源变化即失效，应 ID 优先 |

## 8. 兼容策略

- **M1**：伴生模式，运行时替换 `EffectiveChain` / `PickIndex`（仅法师），复用其按钮与信道；不改其文件。
- **M3**：独立模式，自建按钮与信道；小六月可选共存。
- 版本探测：读取 `LiuyueForever.version` 与函数签名；不匹配则只读，不接管。

## 9. 结论

小六月的价值在**执行层**（安全信道、一键交互、生态），不在**策略层**（法师 APL 与条件引擎）。本项目的策略层是彻底重写；执行层先复用、后独立。

这也解释了为什么"再加几条规则"不够：规则需要条件代数，条件需要状态模型，状态需要测试与观测。缺一层，整体就不可靠。
